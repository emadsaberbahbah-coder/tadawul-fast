# Final board funding repair — review evidence

This proposed change prevents stability research seats from reserving capital and prevents a board with zero executable tickets from retaining projected gain, funded counts, or unrelated deposit/rotation requests. All examples and tests use synthetic data. No workbook, broker, deployment, environment, workflow dispatch, or order changes were made during development.

The cockpit requests a research pass through the existing authenticated opportunity endpoint. Python applies the existing qualification and price-check policy and returns unsized research plans independently of the funding ledger. The existing Apps Script stability core chooses membership and advances its counters once. A second request to the same endpoint allocates only the final eligible symbols, before cash, issuer, sector, market, and selection counters are consumed. Python remains the sizing authority. Grace seats and seats whose sizing is suspended reserve nothing.

The second request replays a signed frozen snapshot, including the qualified source rows and any first-pass price-check results. It preserves the original criteria, holdings, cash, proceeds, FX, and upstream metadata basis. The route does not recollect a selector pool or refresh trends, health, news, or provider quotes. The snapshot uses the existing shared application authentication configuration, an HMAC, exact builder version, policy/basis fingerprint, a 180-second maximum age, and five seconds of future-clock tolerance. Signing calls the same `core.config.allowed_tokens()` resolver as normal opportunity authentication, including its token-list precedence. The complete normalized active token set binds primary, backup, and list rotations; ignored credentials do not influence the signature. Missing shared authentication configuration permits research display and withholds allocation; there is no unsigned or per-worker fallback and no new secret.

The hardened fingerprint includes admission, compliance, quote freshness, forecast horizon and trend policy outside the original `TFB_OPP_*`/`TFB_T10_*` families. A changed policy is rejected before allocation, rather than recalculating a frozen plan under different rules. The standard `RENDER_GIT_COMMIT` value also binds the release when available, so a deployment that changes an imported gate module rejects replay even if the builder version is unchanged. No worker or instance identity is included: workers on the same release share valid snapshots.

Signing, basis comparison, and frozen-row comparison canonicalize JSON values with type tags and IEEE-754 numbers. This makes Python `100.0`, JavaScript `100`, negative zero, and equivalent exponent spellings agree without making changed financial values agree. A mounted endpoint test performs an actual Node `JSON.parse`/`JSON.stringify` round trip on a signed request and verifies both successful replay and rejection of numeric tampering.

Finalization reads the authoritative feed verdict before rendering and derives executable spend, primary and parallel gains, weighted blends, funded counts, unallocated cash, audit selection flags, and funding narratives from the final board. It removes stale monetary claims from legacy backend responses, unsupported contracts, request failures, mismatched/expired snapshots, and direct render calls without an approved allocation result. Raw snapshot rows are removed before rendering, selection logs, and downstream consumers. Existing risk thresholds, gate modes, confirmation thresholds, position sizing, venue lots, and ordinary single-pass API requests retain their behavior. Under the new board contract, grace seats always remain research with no allocation; this supersedes the old `DT10_P145_GRACE_SIZING_LEGACY=1` sizing bypass. Stability OFF still permits qualified candidates to reach the existing allocation rules.

A confirmed qualified action with an admissible minimum ticket and a real funding shortfall can still have a capital-call or rotation proposal. Its spend and expected gain remain zero until funded. A policy exclusion cannot become a deposit request. This state is reported as `QUALIFIED_UNFUNDED`; an entirely grace/suspended board remains `HELD` with zero monetary claims.

A main-only manual deployed readback workflow uses the existing backend token and an explicitly blocked synthetic candidate with zero cash. It requires the deployed commit and source versions to match, a signed empty research snapshot to replay successfully, changed cash and FX to fail closed, and the commit to remain unchanged through the check. Its mounted-route bridge exercises the exact probe body through the actual endpoint and verifies no quote or allocation-time acquisition calls. The probe never accesses Sheets or a broker and publishes only a sanitized result. It attests the deployed API contract; it does not attest Apps Script installation, live coverage, or executable workbook decisions.

The hardened version pins are opportunity builder `1.24.1`, advanced-analysis route `4.17.0`, and decision cockpit `1.12.1`. Deployment verifier pins match the Python source. The GitHub Actions workflow header/version is unchanged so independent provider and funding repairs can merge cleanly.

Operational limits are explicit. An actionable board normally adds one bounded builder-only HTTP request; a board with no eligible actions or a withheld feed adds none. Frozen transport is limited to 500 qualified rows and a conservative one-megabyte canonical bound. Overflow keeps research display and withholds money. The second builder pass repeats normalization/gate evaluation and sizing but acquires no new external data. The final board can retain fewer funded tickets when existing risk/funding rules reject an eligible seat; it never promotes an unconfirmed or grace seat to fill a funding vacancy. Confirmation now follows qualifying research observations rather than the earlier cash-limited allocation list, removing budget dependence from the existing day counters.

Deployment must coordinate the Python backend and Apps Script source. Publish/review the branch first; deploy the backend and verify the exact runtime versions, then install the cockpit source and verify its version. Before the new backend is available, the new cockpit fails closed to research with an allocation-unavailable explanation. Read back a fresh feed verdict, board title, funded quantities, gain, unallocated amount, capital/rotation alerts, and matching selection-log rows after refresh. Confirm that the stability counter advances only on a new existing epoch, and that no raw snapshots appear in logs. Check HELD, mixed, and confirmed-unfunded cases using a safe non-order fixture or isolated workbook. No live order should be submitted by these checks.

For a reversible rollout brake, set the existing project's Script Property `DT10_BOARD_FUNDING_MODE=research`. Qualification and stability display continue, allocation HTTP is skipped, and finalization/renderer show zero monetary claims with `funding=research/0exec` and an allocation-disabled explanation. Unset or `enabled` permits the signed replay; unknown values or a failed property read withhold allocation. The brake is checked again after HTTP so a change during a refresh also withholds money. Clearing the brake requires a fresh refresh to generate funded plans; it never restores stale sizes. There is no fallback to the legacy funding behavior.

Rollback the cockpit and backend together to the reviewed base if necessary; restoring the backend alone leaves the new cockpit safely research-only. A coordinated source rollback restores the previous funding behavior and its known limitations, so review the board's monetary claims before acting. This document records development/review evidence; deployment results must be recorded separately.
