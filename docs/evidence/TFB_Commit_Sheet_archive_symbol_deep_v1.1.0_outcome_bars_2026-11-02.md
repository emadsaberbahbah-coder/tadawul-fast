# Commit Sheet: bars for every symbol with an active forecast record (archive_symbol_deep 1.1.0), 2026-11-02

**Scope.** Owner request 2 Nov 2026 00:13 Riyadh: "learning is slow"; "improve today, results tomorrow". The BigQuery outcome engine (views 1.5.0, built in parallel) scores every overdue forecast record of `v_performance_log` from `symbol_bars_daily`. Measured on 1 Nov: 13,856 active records across 1,376 symbols (5,759 overdue); only 164 of those symbols have bars, because the deep set (holdings, Top-10 board 30 d, ROI top 50, Market_Leaders: 315 symbols, cap 600) was never meant to cover the forecast book. The engine can therefore score about 30 % of the backlog. This change adds the symbols with an active record to the BARS stage only, behind a new gate that is off by default. Read-only for the workbook and the live system: no decision, gate, floor, executable-count or broker change; the EODHD loads and their budget guard are untouched.

## Findings
| Finding | Why it matters | Fix |
|---|---|---|
| The set query knows nothing about the forecast book: 893 `.US`, 127 suffix-less (plain US tickers plus futures `ALI=F` and FX `AUDCHF=X`), 127 `.SR`, 57 `.T`, 55 `.HK`, 23 `.L` and 118 others with active records; 27 of the 893 US names and 119 of the 127 Saudi names have bars. | Every overdue record of a symbol without bars stays unscored: the learning loop sees 30 % of its own evidence. | `SET_SQL` gains one union, `SELECT DISTINCT symbol, 'outcome' FROM v_performance_log WHERE status = 'active'`; the five v1.0.0 unions are byte-identical. `build_sets()` is unchanged and ignores the new rows. |
| A best-effort set of ~1,200 symbols must never cost the deep set its nightly refresh. | A Yahoo throttle late in the run, or a slow night, could push the job past the 45-minute timeout before the one load. | The deep set is read FIRST; the outcome set only after it, through the same `collect_bars`, one symbol at a time, and it stops asking after `OUTCOME_TIME_S` = 1,500 s (25 min). The symbols not reached are reported as "not asked", never as missing. |
| The 80 % rule must stay the deep set's. | Counting the outcome set in the share would let 1,200 best-effort answers hide a failing deep set, or let 1,200 unknown listings block a healthy one. | `share` is computed over the deep set exactly as in v1.0.0. Under 80 %: the outcome set is not even read (write mode), nothing is loaded, yesterday's table stays, exit 1. The outcome set is never a reason to fail. |
| One table, one load. | Two `WRITE_TRUNCATE` loads of the same table would leave only the second set. | The outcome rows (`set_reason = 'outcome'`) are appended to the deep rows and the one existing load replaces the table. |
| Futures and FX in the suffix-less records. | `ALI=F`, `AUDCHF=X` are not listings; a crash on them would stop the run. | `build_outcome_set()` skips any symbol with `=` and anything `_SYMBOL_RE` refuses; `=`-symbols are never asked (D11b). Their records stay unscored (a follow-up decides whether the engine should see FX / futures). |
